第 1 章 现代 Web

我所构想的万维网（Web），我们目前尚未真正见到。 未来依然远比过去更加宏大。

蒂姆·伯纳斯-李（Tim Berners-Lee）

本章预览

曾几何时，Web 既小巧又简单。 开发者们乐此不疲地把 PHP、HTML 和 MySQL 调用全都塞进单个文件里， 然后自豪地招呼大家来看看自己的网站。 但随着时间推移，Web 增长到了数以亿计、甚至数不清的页面——早年间的小游乐场， 如今已经演变成了一座由无数主题公园构成的元宇宙。

在本章中，我将指出在现代 Web 中变得愈发重要的几个核心领域：

  • 服务与 API（Services and APIs）

  • 并发（Concurrency）

  • 分层架构（Layers）

  • 数据（Data）

下一章将展示 Python 在这些领域提供了哪些支持。 在那之后，我们将深入探索 FastAPI Web 框架， 看看它能为我们带来什么。

服务与 API

Web 是一张庞大的连接网络。 尽管大量活动仍然发生在内容（content）端——如 HTML、JavaScript、图片等——但人们正越来越重视用于连接万物的应用程序编程接口（Application Programming Interface，简称 API）。

通常情况下， Web 服务（service）负责处理底层的数据库访问和中层的业务逻辑 （这两者常被统称为后端［backend］）， 而 JavaScript 或移动应用则提供丰富的顶层前端（frontend） （即交互式用户界面）。 前端与后端这两个世界已经变得愈发复杂且分化明显， 通常需要开发者专精于其中一方。 如今想要成为一名全栈（full stack）开发者，已经比过去难得多了。1

这两个世界通过 API 进行通信。 在现代 Web 中，API 设计与网站本身的设计同等重要。 API 是一份契约，类似于数据库模式（schema）。 定义和修改 API 如今已是一项核心工作。

API 的种类

每一个 API 都会定义以下两部分内容：

协议（Protocol）

控制结构

格式（Format）

内容结构

随着技术从孤立的单机演进到多任务系统， 再到联网的服务器，衍生出了多种多样的 API 实现方式。 你在开发生涯中很可能会接触到以下一种或多种方式， 因此在进入本书的主角——HTTP 及其生态伙伴之前， 我们先对它们作一个简要总结：

  • 在网络普及之前，API 通常意味着非常紧密的调用关系， 比如对使用同一种编程语言编写的库（library）发起函数调用——例如在数学库中计算平方根。

  • 远程过程调用（Remote Procedure Call，简称 RPC）的发明，是为了能够调用本机或其他机器上其他进程中的函数， 并且让调用体验就像调用本应用内部的函数一样自然。 目前非常流行的一个代表是 gRPC。

  • 消息传递（Messaging）通过管道在多个进程之间发送小块数据。 消息可以是类似动词的“命令（command）”， 也可以只是表示发生了某个值得关注的、类似名词的“事件（event）”。 当前流行的消息传递方案（从轻量级工具包到完整的服务端系统跨度很大）包括： Apache Kafka、 RabbitMQ、 NATS 以及 ZeroMQ。 其通信过程可以遵循不同的模式：

    请求-响应（Request-response）

    一对一通信，就像 Web 浏览器调用 Web 服务器一样。

    发布-订阅（Publish-subscribe，简称 pub-sub）

    发布者（publisher）发出消息， 而订阅者（subscriber）根据消息中的某些数据（如主题 subject）对各自感兴趣的消息做出响应。

    队列（Queues）

    类似于发布-订阅模式，但在订阅者池中，只有其中一个订阅者会获取该消息并执行处理。

以上任何一种机制都可以与 Web 服务配合使用——例如，用来执行发送电子邮件或生成缩略图这类耗时的后端任务。

HTTP

伯纳斯-李（Berners-Lee）为他的万维网（World Wide Web）提出了三大核心组件：

HTML

一种用于展示数据的标记语言

HTTP

一种客户端-服务器通信协议

URL

一种针对 Web 资源的寻址方案

虽然事后看来这些设想似乎理所当然， 但事实证明，它们组成了一套极其有用的黄金搭档。 随着 Web 的演进，人们不断进行各种尝试， 其中一些想法（例如 IMG 标签）在优胜劣汰的竞争中存活了下来。 而当需求变得愈发明确时， 人们便开始认真地制定各项标准了。

REST(ful)

罗伊·菲尔丁（Roy Fielding）在其博士学位论文的其中一章里，定义了表述性状态转移（Representational State Transfer，简称 REST）——一种使用 HTTP 的架构风格（architectural style）。2 尽管这一概念经常被引用，但它在很大程度上一直被人们误解。

后来，业界演化出了一套大致达成共识的改编实践，并在现代 Web 中占据了主导地位。 它被称为 RESTful， 具有以下特征：

  • 使用 HTTP 和客户端-服务器协议

  • 无状态（Stateless，即每次连接都是相互独立的）

  • 可缓存（Cacheable）

  • 基于资源（Resource-based）

资源（resource）是你可以区分并对其执行操作的数据。 Web 服务会为它想要对外暴露的每一个功能提供一个端点（endpoint）——即一个特定的 URL 与一个 HTTP 动词（verb，代表操作动作）的组合。 端点也被称为路由（route）， 因为它负责将该 URL 路由（分发）到对应的处理函数。

数据库用户都很熟悉代表四类基本操作的缩写词 CRUD：创建（create）、读取（read）、更新（update）和删除（delete）。 HTTP 动词与 CRUD 操作有着非常直观的对应关系：

POST

创建（写入）

PUT

完全修改（替换）

PATCH

部分修改（更新）

GET

唔，获取（读取、检索）

DELETE

呃，删除

客户端向 RESTful 端点发送 请求（request）时， 可以将数据放在 HTTP 报文的以下几个区域之一：

  • 请求头（Headers）

  • URL 字符串（The URL string）

  • 查询参数（Query parameters）

  • 请求体数据（Body values）

相应地，HTTP 响应（response）会返回以下内容：

  • 一个整型的状态码（status code）， 其不同号段的含义如下：

    100 号段（100s）

    信息提示，请继续请求

    200 号段（200s）

    成功

    300 号段（300s）

    重定向

    400 号段（400s）

    客户端错误

    500 号段（500s）

    服务端错误

  • 各种响应头（Headers）

  • 响应体（Body），它可以是空的、单块完整的，或者是分块传输的（chunked，即分成连续的数据块返回）

至少有一个状态码是彩蛋： 418（我是一个茶壶） 按照设定应当由联网的茶壶返回—— 当有人请求它煮咖啡的时候。

你会找到许多关于 RESTful API 设计的网站和书籍， 它们都提供了实用的经验法则。 本书也会在后续章节中陆续分享一些设计技巧。

JSON 与 API 数据格式

前端应用程序可以与后端 Web 服务交换纯 ASCII 文本， 但我们该如何表达像“元素列表”这样的数据结构呢？

就在我们真正开始迫切需要它的时候， JavaScript 对象表示法（JavaScript Object Notation，简称 JSON）应运而生——这是另一个解决了重大问题、事后看来又显得顺理成章的简洁创意。 虽然其中的 J 代表 JavaScript， 但它的语法看起来也和 Python 非常相似。

JSON 已经在很大程度上取代了 XML 和 SOAP 等早期尝试。 在本书的其余部分中，你将看到 JSON 是 Web 服务默认的输入与输出格式。

JSON:API

如今，RESTful 设计与 JSON 数据格式的结合已经非常普遍。 但其中仍然存在一些模棱两可的弹性空间， 常引发技术极客之间的争论。 近年提出的 JSON:API 规范提案， 就旨在进一步收紧并明确相关规范。 本书将采用较为宽松的 RESTful 方法， 但如果你所在的团队经常因为接口规范争执不下，那么 JSON:API 或类似的严格规范可能会很有帮助。

GraphQL

对于某些特定场景而言，RESTful 接口可能会显得有些繁琐。 Facebook（现为 Meta）设计了 图查询语言（Graph Query Language，简称 GraphQL）， 用来编写更加灵活的服务查询。 本书不会深入讨论 GraphQL， 但如果你发现 RESTful 设计无法满足你的应用需求，不妨去了解一下它。

并发

除了面向服务架构的普及之外， Web 服务连接数量的急剧增长，也对运行效率和扩展能力提出了越来越高的要求。

我们希望改善以下两项指标（降低延迟、提升吞吐）：

延迟（Latency）

前期的等待时间

吞吐量（Throughput）

服务与其调用方之间每秒传输的字节数

在早期的 Web 时代，3 人们曾梦想着能够同时支持数百个并发连接， 后来又为“C10K 问题（单机一万并发连接）”焦虑不已， 而如今则动辄假设要同时处理数百万个连接。

并发（concurrency）一词并不等同于完全的并行（parallelism）。 在单个 CPU 中，并不会在同一纳秒内真正同时执行多个处理过程。 相反，并发主要是为了避免忙等待（busy waiting，即在收到响应之前让 CPU 空闲等待）。 CPU 的速度极快，但网络和磁盘的速度却比它慢上数千乃至数百万倍。 因此，每当我们与网络或磁盘通信时，我们绝不希望只是两眼发直地干坐在那里等待它响应。

普通的 Python 执行方式是同步的（synchronous）：一次只做一件事， 严格按照代码指定的顺序执行。 但有时我们希望它是异步的（asynchronous）： 先做一点第一件事， 再做一点第二件事， 然后切回第一件事，依此类推。 如果我们的所有代码都在占用 CPU 进行计算（即 CPU 密集型，CPU bound）， 那就确实没有多余的空闲时间来进行异步切换。 但如果我们执行的操作需要让 CPU 等待某个外部操作完成（即 I/O 密集型，I/O bound），我们就可以采用异步方式。

异步系统提供了一个事件循环（event loop）： 针对慢速操作的请求会被发送出去并记录在案， 但我们不会阻塞 CPU 去傻等它们的响应。 相反，事件循环在每一轮遍历中都会执行一些可以立即处理的任务， 而在此期间返回的任何响应，则会在下一轮循环中得到处理。

这种机制带来的性能提升可能是极其惊人的。 在本书后面的章节中，你将看到 FastAPI 对异步处理的支持， 是如何让它比传统的 Web 框架快得多的。

当然，异步处理并不是万能魔法。 你仍然需要小心谨慎，避免在事件循环中执行过多消耗 CPU 的密集计算工作， 因为那会拖慢整体的一切运行。在本书后续内容中，你将看到 Python 的 async 和 await 关键字的具体用法， 以及 FastAPI 是如何允许你将同步处理与异步处理混合使用的。

分层架构

《怪物史瑞克》（Shrek）的影迷可能还记得，史瑞克曾提到他的性格是有层次（layers）的， 而驴子回答道：“像洋葱一样？”

好吧，既然食人魔和催泪的蔬菜都能分层次， 软件自然也可以。 为了管理规模和复杂度， 许多应用程序长期以来一直采用所谓的 三层模型（three-tier model）。4 这并不是什么新鲜概念。 虽然不同资料中的术语有所差异，5 但在本书中，我将采用以下简洁的术语划分（见图 1-1）：

Web 层（Web）

基于 HTTP 的输入/输出层，负责组装客户端请求、调用服务层（Service Layer）并返回响应

服务层（Service）

业务逻辑层，在需要时会调用数据层（Data layer）

数据层（Data）

负责访问数据存储和其他外部服务

模型模块（Model）

供所有层级共享的数据定义

Web 客户端（Web client）

Web 浏览器或其他 HTTP 客户端软件

数据库（Database）

数据存储系统，通常是 SQL 或 NoSQL 服务器

这些组件将帮助你平滑地扩展站点规模， 而无需推倒重来。 它们并不是量子力学定律， 所以请将它们视为本书阐述架构时的指导原则。

各个层级之间通过 API 相互通信。 这些 API 可以是对独立 Python 模块的简单函数调用， 也可以通过任意方式访问外部代码。 正如我前面展示的，这可以包括 RPC、消息队列等等。 在本书中，我假设所有代码运行在单个 Web 服务器中， 由 Python 代码直接导入（import）其他 Python 模块。 职责分离与信息隐藏均由模块机制来处理。

Web 层是用户通过客户端应用程序和 API 直接接触的一层。 我们通常探讨的是带有 URL、并使用 JSON 编码请求与响应的 RESTful Web 接口。 但除了 Web 层之外，你也可以并排构建替代性的纯文本（或命令行界面，CLI）客户端。 Python 的 Web 层代码可以导入服务层（Service-layer）模块， 但不应当直接导入数据层（Data）模块。

服务层（Service layer）包含该网站所提供功能的实际业务逻辑细节。 这一层本质上看起来就像一个库（library）。 它会导入数据层模块来访问数据库和外部服务， 但不应当知晓底层的数据存储细节。

数据层（Data layer）通过文件读写或对其他服务的客户端调用，为服务层提供数据访问能力。 系统中也可以同时存在多个替代性的数据层， 与同一个服务层进行通信。

模型模块（Model box）并不是一个实际的调用层， 而是供各个层级共享的数据定义来源。 如果你在各层之间只传递 Python 内置的数据结构，则不需要单独的模型模块。 但正如你稍后将看到的，FastAPI 内置集成了 Pydantic， 使我们能够定义出具有诸多实用特性的数据结构。

为什么要做这样的划分呢？ 在众多原因之中，最核心的优势在于每一层都可以：

  • 由相应领域的专家编写。

  • 独立进行测试。

  • 被替换或扩展：例如你可以在原有的 Web 层旁边，使用 gRPC 等不同的 API 再添加第二个 Web 接入层。

请遵循《捉鬼敢死队》（Ghostbusters）里的一条铁律： 不要让质子流交叉（Don’t cross the streams）。 也就是说，不要让 Web 细节泄漏到 Web 层之外， 也不要让数据库细节泄漏到数据层之外。

你可以把分层（layers）想象成一个垂直堆叠的结构， 就像《英国家庭烘焙大赛》（Great British Bake Off）里的多层蛋糕一样。6

以下是保持层级分离的几个重要原因：

  • 如果你不把各层分离开来，就会印证那句著名的编程梗：现在你有两个问题了（Now you have two problems）。

  • 一旦各层的逻辑混杂在一起，日后想要再把它们拆分出来将会极其困难。

  • 如果代码逻辑纠缠不清，你必须同时精通两个或更多专业领域的知识，才能读懂代码并编写测试。

顺便提一句， 尽管我把它们称为层（layers）， 但你不必先入为主地认为某一层就一定在另一层的“上方”或“下方”， 也不必认为指令只能顺着重力方向流动。 这可是“垂直沙文主义”！ 你完全可以把各个层看作是横向通信的方框（见图 1-2）。

无论你如何具象化地想象它们， 这些方框/层级之间唯一的通信路径就是图中的箭头（即 API）。 这一点对于测试和调试至关重要。 如果一座工厂里存在未记录在案的暗门， 守夜人迟早会撞见意想不到的惊吓。

Web 客户端与 Web 层之间的箭头使用 HTTP 或 HTTPS 协议，主要传输 JSON 文本。 数据层与数据库之间的箭头使用特定于数据库的协议，并传输 SQL（或其他查询）文本。 而各层内部之间的箭头，则是传递数据模型的函数调用。

此外，在这些箭头中流动的推荐数据格式如下：

客户端（Client） ⇔ Web 层

承载 JSON 的 RESTful HTTP

Web 层 ⇔ 服务层（Service）

数据模型（Models）

服务层（Service） ⇔ 数据层（Data）

数据模型（Models）

数据层（Data） ⇔ 数据库与外部服务

专用 API（Specific APIs）

基于我个人的开发经验， 我选择按照这样的架构来组织本书的各个主题。 这套方案切实可行，并且已经成功支撑过相当复杂的站点， 但它并非金科玉律。 你完全可能拥有更好的设计方案！ 无论你采用何种方式， 以下几个核心要点都是相通的：

  • 隔离特定领域的实现细节。

  • 在层级之间定义标准的 API。

  • 不要走捷径作弊；不要让底层细节泄漏。

有时候，决定某段代码究竟最适合放在哪一层确实颇具挑战。 例如，第 11 章探讨了身份认证（authentication）与授权（authorization）的需求及其实现方式——究竟是作为 Web 层与服务层之间的一个额外层级， 还是放在其中某一层内部。 软件开发有时既是一门科学，也是一门艺术。

数据

Web 经常被用作关系型数据库的前端， 不过如今也演进出了许多其他存储和访问数据的方式， 例如 NoSQL 或 NewSQL 数据库。

然而在数据库之外， 机器学习（machine learning，简称 ML）——或者说深度学习（deep learning），乃至统称的 人工智能（AI）——正在从根本上重塑整个技术版图。 大型模型的开发需要对数据做海量的整理与加工，这一过程在传统上被称为提取、转换和加载（extract, transform, load，简称 ETL）。

作为一种通用的服务架构， Web 能够帮助解决机器学习系统中许多繁琐的工程细节。

本章回顾

Web 使用着形形色色的 API，但其中尤以 RESTful API 最为普遍。 异步调用能够实现更好的并发性能， 从而加快整体处理速度。 Web 服务应用程序通常规模较大，适合划分为多个层级。 数据本身也已经发展成为一个举足轻重的独立领域。 所有这些概念在 Python 编程语言中都有相应的解决方案， 我们将在下一章中展开介绍。
